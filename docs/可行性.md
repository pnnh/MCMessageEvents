# MCMessageEvents 可行性分析（MVP）

目标：在 Minecraft 1.21.1 / NeoForge 上，将**聊天区内容**与**日志输出**暴露为可被 KubeJS（及原生 NeoForge 监听方）消费的事件；模组可在客户端或服务端单独安装。

## 结论

**可行。** MVP 应以「聊天 HUD 全量消息 + 可选 Log4j 桥」为主路径，KubeJS 作为软依赖提供友好事件组；不强制客户端与服务端同时安装。

## 聊天区内容

| 来源 | 客户端 | 专用服务端 | 捕获方式（规划） |
|------|--------|------------|------------------|
| 玩家发出的聊天 | 有 | 有 | NeoForge `ClientChatEvent` / `ServerChatEvent` |
| 服务端下发到聊天 HUD | 有 | 有（广播前） | `ClientChatReceivedEvent`；服务端 `PlayerList#broadcast*` / system message 钩子 |
| 系统消息、命令反馈、死亡消息等 | 有 | 部分 | 客户端以「进入聊天组件」为准更完整 |

客户端安装时，以**最终进入聊天 HUD 的消息**为准，覆盖用户发送与服务器下发；服务端单独安装时，覆盖本机可观测的聊天/系统广播，不虚构客户端 HUD。

## 日志内容

游戏「聊天区」与 Log4j/控制台日志是两条通道。

- **聊天区日志式消息**（`/say`、系统提示进 HUD）：归入聊天事件，MVP 必做。
- **真正的 logger 输出**（`LOGGER.info` 等到控制台/latest.log）：需自定义 Log4j Appender 或桥接；噪声大，MVP 做成**可配置开关**，默认关闭或仅 `INFO+`，并标注 logger 名与 level。

## KubeJS 集成

1. **零硬依赖路径**：本模组发布 NeoForge 总线事件；有 KubeJS 时可 `NativeEvents.onEvent("…EventClass", …)`。
2. **软依赖友好 API（推荐）**：`kubejs.plugins.txt` 注册 `EventGroup`（如 `MessageEvents.chat` / `MessageEvents.log`）。主 `@Mod` 类不得直接引用 KubeJS 类型，避免未安装 KubeJS 时崩溃。`mods.toml` 中 `kubejs` 标为 `optional`。

KubeJS 7.x（1.21 NeoForge）已支持可重载 NativeEvents 与插件 `registerEvents`，与本方案兼容。

## 双端可选安装

- `side=BOTH`，`displayTest=IGNORE_ALL_VERSION`（与参考模组一致的独立安装语义）。
- 客户端专用代码放入 `Dist.CLIENT` 订阅或独立类；专用服务端不加载客户端类。
- **不**假设对端也安装本模组；不做「仅本模组私有协议」的跨端同步（MVP 范围外）。若未来需要「服务端捕获 → 推到客户端脚本」，另开特性规格。

## 主要风险

1. **重复投递**：同一条消息可能在发送端与接收端各触发一次；事件载荷需带 `side` / `phase`（outbound/inbound）以便脚本去重。
2. **日志风暴**：未过滤的 Log4j 桥会拖垮脚本；必须限流/级别过滤。
3. **KubeJS 版本漂移**：`kubejs_version` 在 plan 阶段钉死后做一次 `runClient`/`runServer` 冒烟。
4. **组件序列化**：聊天多为 `Component`；脚本侧至少提供纯文本，可选保留结构化字段。

## MVP 边界

**纳入**：双端独立安装；聊天 HUD 消息事件；可选 logger 桥；KubeJS 软依赖事件组；无 KubeJS 时模组仍可加载（仅无脚本监听）。

**不纳入**：改写/取消消息（只读观察，除非后续规格明确）；跨端私有同步；非聊天 GUI 文本；完整审计存储。
